# Redmine 标签自动化测试设计

## 1. 目标

本测试设计验证标签自动化从规则配置、标签来源、字段裁决、本地保存到真实工时同步的完整链路。测试使用独立 Redmine 测试服务和隔离 DiaryApp profile，不依赖生产项目，不在报告、日志或提交内容中记录 API Key。

测试重点不是重复纯逻辑单元测试，而是发现以下集成问题：

- UI 规则顺序、启用状态和“强制修改”没有正确保存或重载。
- 标签添加入口没有调用自动化协调器，或加载已有事项时错误地再次执行规则。
- Activity、Issue 候选与远程服务状态不同步。
- 规则生成的本地 Tracker 草稿没有随事项事务保存，或无法用于后续工时同步。
- 多实例、无效目标和部分失败错误地阻断了核心标签编辑。

## 2. 测试数据

运行以下命令幂等创建或补齐测试数据：

```bash
node Tools/redmine-tag-automation-fixtures.mjs
```

凭据默认从仓库根目录的 `redmine_testing.txt` 读取：第一行为服务地址，第二行为 API Key。该文件已加入 `.gitignore`。脚本只输出项目、问题 ID 和主题，不输出 API Key；结果清单写入 `.build-tmp/redmine-tag-automation-fixtures.json`。

稳定夹具分为三组：

| 项目标识 | 用途 | 稳定问题 |
| --- | --- | --- |
| `diaryapp-tag-auto-basic` | 默认值、保留用户值、强制覆盖 | `TA-BASIC-01` 至 `TA-BASIC-04` |
| `diaryapp-tag-auto-conflict` | 同标签多规则冲突、多标签添加顺序 | `TA-CONFLICT-01` 至 `TA-CONFLICT-04` |
| `diaryapp-tag-auto-lifecycle` | 模板应用/更新、重复事项、保存重载和同步 | `TA-LIFECYCLE-01` 至 `TA-LIFECYCLE-06` |

稳定项目和问题视为只读夹具，不在自动化结束时删除。需要验证创建 Issue 的用例继续使用带时间戳的临时主题，与标签自动化套件分离。

## 3. 测试层次

### 3.1 纯逻辑测试

保留 `RedMineTagDefaultsTests` 作为快速门禁，覆盖：

- 空字段按规则配置顺序填充。
- 关闭强制修改时不覆盖已有 Activity 和 Issue。
- 开启强制修改时覆盖已有值。
- 禁用规则、其他标签和无效目标跳过。
- 第一条目标无效时继续选择后续有效规则。
- 同字段多条有效规则由第一条获胜并记录冲突。

### 3.2 ViewModel 和持久化测试

使用内存数据库和伪 Tracker 扩展覆盖：

- 手动添加、模板添加、重复事项分别传递正确的 `TagAddSource`。
- “应用模板”覆盖标题和工时、清空旧标签，并按 `DefaultWorkTags` 保存顺序触发 `Template` 来源规则。
- “更新自模板”只补空标题和零工时；仅当事项当前无标签时添加模板标签并触发规则，已有标签时不改标签也不触发。
- 模板中缺失的标签 ID 被跳过；有效主标签和次标签的相对顺序保持稳定。
- 新事项保存前暂存的标签自动化在事项创建后按添加顺序补发。
- 已有标签重复添加、加载已有事项和删除标签不执行规则。
- 自动化结果随 Tracker 扩展草稿进入本地事务；保存失败不产生半完成绑定。
- 保存后重载保持用户最终值，不再次应用默认值。

### 3.3 真实 Redmine CDP 测试

新增独立套件 `ui-redmine-tag-automation`，使用加载插件的隔离 profile。稳定问题通过主题前缀定位，不硬编码远程 ID。

| 编号 | 场景 | 配置和操作 | 期望结果 |
| --- | --- | --- | --- |
| TA-01 | 空字段默认填充 | 标签规则指向 `TA-BASIC-01` + Development，关闭强制修改；新建事项后添加标签 | Issue、Activity 自动填充，规则结果无错误 |
| TA-02 | 保留用户选择 | 先选择 `TA-BASIC-03` + Design，再添加指向 `TA-BASIC-01` + Development 的非强制标签 | 原 Issue 和 Activity 保持不变 |
| TA-03 | 强制覆盖 | 先选择 `TA-BASIC-03` + Design，再添加指向 `TA-BASIC-04` + Development 的强制标签 | 两个字段都替换为规则目标 |
| TA-04 | 同标签多规则冲突 | 同一标签依次配置 `TA-CONFLICT-01`、`TA-CONFLICT-02` | 第一条规则获胜；结果记录冲突；标签仍添加成功 |
| TA-05 | 无效目标回退 | 第一条规则使用不存在的 Issue/Activity ID，第二条规则指向 `TA-CONFLICT-01` + Design | 显示失效目标，后续有效规则填充字段，核心编辑不被阻断 |
| TA-06 | 禁用规则 | 禁用指向 `TA-BASIC-04` 的规则后添加标签 | Tracker 字段不变化 |
| TA-07 | 多标签添加顺序 | 标签 A 指向 `TA-CONFLICT-03`，标签 B 指向 `TA-CONFLICT-04`；分别按 A→B、B→A 添加 | 每一步基于前一步状态；强制策略和最终值符合添加顺序 |
| TA-08 | 应用带标签模板 | 当前事项已有其他标题、工时和标签；模板含主标签，规则指向 `TA-LIFECYCLE-01` | 标题、工时和标签被模板替换，规则以 `Template` 来源执行并保存绑定 |
| TA-09 | 应用主次标签模板 | 模板依次保存主标签和次标签，分别指向 `TA-LIFECYCLE-01`、`TA-LIFECYCLE-02` | 两个标签按模板顺序添加；规则裁决顺序与 `DefaultWorkTags` 一致 |
| TA-10 | 更新自带标签模板（空事项） | 当前标题为空、工时为零且无标签；模板标签指向 `TA-LIFECYCLE-03` | 只补空字段并添加模板标签，规则以 `Template` 来源执行 |
| TA-11 | 更新自带标签模板（已有内容） | 当前已有标题、非零工时和标签，再执行“更新自模板” | 现有字段和标签不被覆盖，不执行模板标签规则 |
| TA-12 | 模板失效标签边界 | 模板保存后停用标签，并构造一个已删除标签 ID | 候选不再允许新增停用标签；应用时缺失 ID 被跳过，其他有效标签仍按顺序处理；停用标签的执行语义单独记录以便产品决策 |
| TA-13 | 重复事项来源 | 原事项标签目标为 `TA-LIFECYCLE-04`，执行“重复当前事项” | 新事项重新执行规则，不复用原远程上传状态 |
| TA-14 | 保存重载 | 自动填充后手动改为 `TA-LIFECYCLE-05`，保存并切换日期后返回 | 用户最终值保留；加载不再次触发规则 |
| TA-15 | 删除标签 | 自动填充后删除标签 | Activity 和 Issue 不反向清空或恢复 |
| TA-16 | 真实同步 | 规则指向 `TA-LIFECYCLE-06` + Development，填写非零工时并同步 | Redmine 新增一次工时；本地状态为同步成功；重复同步被拒绝 |
| TA-17 | 实例禁用 | 保存规则后禁用 Redmine 实例，再添加标签 | 不创建该实例编辑扩展，不报告规则执行失败 |
| TA-18 | 双实例隔离 | 两个 Redmine 实例对同一标签配置不同 Issue | 两个实例各自得到自己的目标，互不覆盖 |

## 4. 套件编排

建议将真实测试拆为三个阶段，失败时更容易定位：

1. `configuration`：创建标签和规则，验证启用、强制修改、顺序以及两个编辑入口保存一致。
2. `application`：执行 TA-01 至 TA-15，只写隔离本地数据库，不提交远程工时，其中 TA-08 至 TA-12 为带标签模板专项。
3. `upload`：执行 TA-16 至 TA-18；TA-16 会产生远程工时，必须串行运行并记录远程 ID 摘要。

套件启动前必须执行夹具脚本，并确认三个项目和十四个问题均存在。若夹具缺失、Redmine 不可达或 API 用户权限不足，套件应在任何 UI 写入之前失败。

## 5. 隔离和清理

- 每次运行使用新的 DiaryApp profile，并从加密 seed profile 复制 Tracker 配置。
- 本地标签、模板和事项名称追加本次运行戳，测试完成后直接删除隔离 profile。
- 稳定 Redmine 项目和问题不删除、不关闭、不改名；自动化只读取它们作为规则目标。
- 工时同步使用非零且容易识别的小数工时，并将本地事项标题加运行戳；报告只记录问题 ID、工时记录 ID和耗时摘要。
- 无效目标使用明显超出夹具范围的 ID 构造配置，不通过删除稳定问题制造失效状态。
- 远程服务异常时禁止自动重试写入；结果未知沿用应用现有同步状态语义。

## 6. 门禁建议

- 纯逻辑与 ViewModel 测试纳入普通 CI。
- `configuration` 和 `application` 可在具有测试 Redmine 的内部定期任务运行。
- `upload` 会产生真实远程记录，只在手动发布前或专用夜间任务串行运行。
- 常规 `ui-redmine-full` 继续负责项目管理、Issue 创建、配置加密和基础工时同步；新套件只负责标签自动化矩阵，避免单个套件过长且失败难定位。

## 7. 当前已验证基线

2026-08-27 已将常规 `ui-redmine-full` 扩展到 14 个步骤，并在 Linux X11、1280×800、隔离 SQLite profile 与真实 Redmine 服务上全部通过。报告为 `ui-redmine-full-2026-08-27T11-10-05-194Z.json`。

本次真实验证覆盖：

- 新建规则默认启用并默认强制修改，标签、活动和 Issue 选择后可保存并在实例重建后生效。
- 规则编辑卡片在最小支持窗口下使用两行布局，没有字段或删除按钮重叠。
- 空事项执行“从模板更新”会补标题、工时和模板标签，并以 `Template` 来源触发 Tracker 默认值。
- 已有标题、非零工时和标签时执行“从模板更新”不会覆盖现有内容，也不会执行模板标签规则。
- “应用模板”会替换标题、工时和标签，并触发规则填充 Issue 与活动。
- 手动添加同一自动化标签、保存本地事项、真实工时同步、防重复入口、仅本地删除警告、配置加密和管理页响应速度继续通过。

独立 `ui-redmine-tag-automation` 仍用于 TA-02 至 TA-07、TA-12 至 TA-15、TA-17 和 TA-18 等冲突、失效目标、生命周期及多实例组合，不与上述基础端到端基线重复。
