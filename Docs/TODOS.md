## 阶段 9：脚本系统落地

设计文档：[`ScriptSystemDesign.md`](ScriptSystemDesign.md)

目标：将当前 `Diary.ScriptBase` 的接口草案落地为可发现、可编译、可执行、可诊断且受权限控制的脚本系统，
同时为日记批处理、编辑器工作流和 Tracker 只读联动提供稳定宿主边界。

设计约束：

- 脚本不能访问核心数据库连接、DI 容器、`App` 实例或 Avalonia 控件。
- 模板由宿主/编辑器负责选择、应用和持久化，脚本不能选择、创建、修改、删除或应用模板。
- 编辑器脚本使用结构化目标表达年、季度、月、日和事项上下文；日期目标由宿主解析为范围，事项目标传递安全快照。
- Tracker 目标必须使用 `PluginId + InstanceId` 复合身份，不能只使用显示名称或单独实例 ID。
- 脚本异常、编译失败、超时和权限拒绝只能影响当前脚本执行，不能阻止核心程序运行。
- 远程 Tracker 写入默认需要明确授权和确认；当前已实现查询、受控日志项/模板日志项创建和系统交互，远程 Tracker 写入仍未实现。
- 工作记录采用追加式模型；脚本自动化不提供删除或直接改写历史记录，错误更正通过可追溯的修正/冲正记录表达。
- 面向脚本作者的 SDK 按应用命令、编辑器目标、自动化触发等功能提供不同程序入口，底层 Worker 协议保留统一执行适配层。

## 阶段 9.10：脚本 API 用户体验和功能入口优化

设计评审：ScriptApiOptimization.md

目标：在保持所有脚本默认通过 Worker、工作记录追加式和现有 V1 兼容性的前提下，
按脚本功能提供清晰的程序入口，统一跨语言宿主 API 语义，降低脚本作者的学习和维护成本。

实施原则：

- IScriptProgramV1.ExecuteAsync(request, context) 继续作为 Worker 和运行时的底层兼容入口，不直接作为唯一的 SDK 用户入口。
- 应用命令、编辑器目标、自动化触发和后续查询/报表脚本使用不同的强类型或明确命名入口。
- 不为脚本自动化增加删除或直接修改历史工作记录的能力；如确有更正需求，采用追加式修正/冲正模型并保留原始记录。
- 新 API 必须同时定义 C#、Lua、Python 的入口语义、输入字段、错误代码、取消行为和副作用边界。
- 每个阶段完成后同步更新三种语言 API 文档和对应契约测试；本阶段计划不替代实现完成状态。

### 9.10.1 功能入口契约

依赖：现有 V1 ScriptDescriptor、ScriptScope、ScriptExecutionRequest 和 Worker 执行协议保持兼容。

- [ ] 定义 ScriptEntryKind，至少区分 Application、Editor 和 Automation；查询/报表入口作为只读扩展预留。
- [ ] 为应用命令脚本定义 ApplicationScriptContext 和 IApplicationScriptV1。
- [ ] 为编辑器目标脚本定义 EditorScriptContext 和 IEditorScriptV1，直接提供目标、日期范围和事项目标快照。
- [ ] 为自动化脚本定义 AutomationScriptContext 和 IAutomationScriptV1，携带触发器类型、事件数据、幂等键和取消信号。
- [ ] 将不同入口适配到现有 IScriptProgramV1，保持 Worker 的执行历史、超时、取消和诊断模型不变。
- [ ] 扩展 metadata/manifest 声明入口类型，入口类型与 Scope、目标类型不一致时在加载阶段拒绝。
- [ ] 明确 Lua/Python 的入口函数或 manifest 入口命名约定，禁止依赖一个通用 main(context) 隐式判断场景。

验收：脚本作者可以根据入口类型获得正确的强类型/结构化上下文；应用脚本不能收到编辑器目标，
编辑器脚本不能伪装成应用脚本；旧 V1 脚本仍可由兼容适配器加载并通过 Worker 执行。

### 9.10.2 统一宿主上下文和 API 外观

依赖：9.10.1 功能入口契约。

- [ ] 设计统一的 ScriptContext 领域外观，明确 Diary、System、Log、Target、Arguments 和 Cancellation 的职责。
- [ ] C# 增加强类型属性访问，保留 GetApi<T>() 作为底层兼容入口，并提供 GetRequiredApi<T>() 的明确失败诊断。
- [ ] Lua/Python 按各自语言习惯映射同一套领域语义，不要求语法相同但要求字段、错误代码和副作用一致。
- [ ] 统一 Title/Comment 的命名语义，明确创建请求与 ScriptWorkItem 返回 DTO 的字段映射。
- [ ] 统一日期、标签过滤、优先级、分页和流式查询的默认值、上限及错误信息。
- [ ] 为模板和 Tracker 实例补充只读发现 API，并支持 UI 复制稳定 ID。

验收：同一功能在三种语言文档中可以按相同的领域概念查找；缺少宿主 API、作用域不适用和宿主未配置时，
用户能得到可区分的结构化诊断。

### 9.10.3 错误、取消和进度模型

依赖：9.10.1 入口上下文、9.10.2 API 外观。

- [ ] 统一 Host API 错误数据结构，至少包含 code、message、category、retryable 和可选 details。
- [ ] C#、Lua、Python 分别定义符合语言习惯的错误表达方式，但保持错误代码和分类一致。
- [ ] 统一取消令牌传播；宿主 API 默认关联当前执行，动态语言提供显式取消状态查询。
- [ ] 明确 Lua 宿主调用在取消和超时时的行为，避免只能等待同步 HostCall 返回。
- [ ] 增加脚本进度报告 API，区分日志、用户通知和执行进度。
- [ ] 为 Worker 终止、宿主调用失败、取消和超时补充脚本作者可读的处理示例。

### 9.10.4 追加式工作记录安全

依赖：9.10.2 统一宿主上下文和 API 外观。

- [ ] 明确并完善日记追加 API 的事务、确认、审计和失败恢复策略。
- [ ] 评估 Tracker 远程写入是否纳入脚本 API；若纳入，先定义副作用、确认、重试和权限边界。
- [ ] 为普通日志项和模板日志项创建增加幂等键，重复提交同一业务动作不产生重复记录。
- [ ] 增加 Preview/DryRun 能力，只返回待追加记录和副作用摘要，不写入数据库。
- [ ] 记录脚本执行产生的追加结果摘要，便于用户判断是否已经成功写入。
- [ ] 明确 Worker 不自动重试带副作用的请求，避免超时后重复创建。
- [ ] 若业务确实需要更正历史记录，设计追加式修正/冲正记录，保留原始记录和关联关系。
- [ ] 明确脚本自动化永不提供删除历史记录和直接改写历史记录的 API。

验收：脚本重复执行、用户手动重试和 Worker 异常后的结果均可判断是否重复追加；预览不会产生数据库副作用；
