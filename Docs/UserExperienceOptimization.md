# 用户体验优化审查

审查日期：2026-08-09

本文从用户角度审查 DiaryApp 当前的日常记录、Tracker 同步、查询、脚本和首次配置流程。
重点不是增加更多功能，而是降低用户理解成本，保证本地工作记录安全，并让远程同步行为可预期、可恢复。

## 总体结论

当前程序的核心链路已经可用：用户可以创建工作记录、填写耗时、绑定 Tracker、查询历史记录，并通过 Worker 执行脚本。

当前最需要优化的不是底层能力，而是三个关键状态没有被清楚地传达给用户：

1. 工作记录是否已经保存到本地。
2. 工时是否已经同步到 Jira、Redmine 等远程系统。
3. 同步失败、部分成功或需要修正时，用户应该如何继续操作。

因此，后续体验优化应优先围绕“本地记录可靠、远程同步可控、失败可以恢复”展开。

## P0：用户信任和数据安全

### 1. 分离本地保存和远程同步状态

编辑器同时提供“保存”和“提交工时”，但切换事项和隐藏页面时也会自动保存当前事项。
当前行为见 `DiaryEditorViewModel.OnSelectedWorkChanging` 和 `OnHide`。

用户容易将“提交”理解为保存，也无法快速判断当前记录是否已经写入本地数据库或远程系统。

建议：

- 编辑过程中显示“未保存”状态。
- 自动保存完成后显示“已保存到本地”。
- 将“提交工时”改为“同步工时”或“上传到 Jira”。
- 每条工作记录显示以下状态之一：
  - 本地已保存
  - 待同步
  - 已同步
  - 同步失败
  - 部分 Tracker 已同步
- 多个 Tracker 同时启用时，分别显示各实例的同步状态。
- 明确提示：远程系统不可用时，仍然可以继续保存本地工作记录。

已完成第一步：工作记录列表和编辑区已显示“本地已保存/未保存”与“待同步/已同步/同步失败/部分同步”等摘要状态；Jira/Redmine 已保存逐 Tracker 最近一次上传状态、错误和尝试时间，并增加“同步结果待确认”状态。批量同步现在会先展示记录预览，允许逐条排除，确认后逐条执行并展示结果；已确认失败的记录可单独重试，结果不确定的记录不会被自动重试。逐 Tracker 状态的详细 UI、跨 Tracker 筛选和结果查询入口仍待后续补充。

### 2. 批量同步前增加预览和确认

批量同步属于可能产生远程追加副作用的操作。由于远程工时通常不容易撤回，执行前必须让用户确认具体记录，执行后也要区分成功、失败和结果不确定。

建议在同步前展示预览：

> 即将同步 5 条记录，共 7.5 小时，涉及 2 个外部系统实例。

预览阶段应支持：

- 查看待同步记录的日期、事项、耗时、Tracker 和 Issue。
- 排除某一条记录。
- 只同步指定 Tracker 实例。
- 确认后执行远程操作。
- 对已经同步或正在同步的记录进行明确说明。

同步完成后应显示逐条结果，而不是只显示成功、失败、跳过的总数：

- 成功记录可以查看远程 ID 和同步时间。
- 失败记录保留“待重试”状态。
- 部分成功时明确指出哪些记录已经产生远程副作用。
- 提供“仅重试失败项”。

已完成批量流程的基础版本：预览列出日期、事项、耗时、Tracker 和当前状态；默认只选择可上传且不是结果不确定的记录；取消预览不会发起远程请求；确认后逐条显示结果，并可仅重试已确认失败项。远程 ID/同步时间、指定 Tracker 实例筛选以及结果不确定项的查询入口仍属于后续恢复体验工作。

### 3. 按上传状态提供直接删除

工作记录允许删除。特别是尚未上传的记录，或确认属于误写的记录，用户应当能够直接删除后重新创建，不需要引入作废或冲正等额外流程。

建议按状态区分操作：

- 未上传、上传失败且确认未产生远程数据、或确认误写的记录：允许直接删除。
- 删除前提示当前上传状态，避免用户把“未上传”和“已上传”混淆。
- 已成功上传的记录：允许删除本地记录，但必须明确提示远程工时不会随之删除，并显示后续处理方式。
- 上传结果不确定的记录：先提示用户查询或重试，避免删除后重复上传。
- 删除后重新计算当天总工时和待上传工时，并刷新关联的 Tracker 本地绑定。

已完成第一步：删除前会根据是否存在已上传 Tracker 绑定显示不同确认文案；对于已上传记录，确认框会明确说明仅删除本地记录，远程工时不会被删除。

Tracker 诊断页中的“删除数据”也应改成更准确的文案，例如“清除本地缓存和绑定”，并明确说明不会删除远程系统中的数据。

### 4. 错误必须能指导用户恢复

数据库连接失败目前主要显示“数据库连接出错，需要检查设置”，缺少直接操作入口。Tracker 刷新、插件启动和远程上传失败也需要统一的恢复路径。

建议错误信息分成三层：

1. 用户结论：发生了什么，是否影响本地记录。
2. 操作建议：重试、打开设置、稍后同步或导出诊断。
3. 技术详情：异常类型、请求 ID、日志和诊断信息，可折叠显示。

典型恢复动作包括：

- 打开数据库设置。
- 重新连接或重新加载插件。
- 重试刚才的同步操作。
- 保留待同步状态，不要求用户重新录入工作记录。

已完成基础恢复入口：数据库不可用时，日记编辑和统计页面会显示具体失败原因、说明本地记录不受影响，并提供“重试连接”“打开数据库设置”“导出诊断日志”；Tracker 诊断页提供实例级重试和诊断日志导出。远程上传失败会保留失败状态并从批量结果中进入仅重试失败项流程，结果不确定项则明确要求查询或人工确认。更细粒度的远程错误分类和一键打开 Tracker 配置仍待后续补充。
- 复制诊断信息供管理员处理。

## P1：提升日常耗时记录效率

### 5. 增加最近使用和快捷复制

工作记录是高频操作，应尽量减少每天重复选择项目和标签的步骤。

建议增加：

- 最近使用的项目。
- 最近使用的标签。
- 复制昨天的记录。
- 复制最近一条记录。
- 按日期复制整天记录。
- 快速记录 30 分钟、1 小时、2 小时。
- 新建记录后自动聚焦标题或耗时输入框。
- 新建同类事项时自动带入最近使用的项目和标签。

现有模板和重复操作可以继续保留，但需要在主界面上更容易发现，不能让用户必须依赖右键菜单或记忆快捷键。

已完成基础版本：日记页提供“复制昨天”，复制前显示条数和总工时并要求确认；复制只带入本地字段和标签，不复用远程 Tracker 绑定。工时编辑提供 15/30 分钟、1/2/4 小时和清零快捷项；新建事项的标签列表会优先展示当天已有记录中最近使用的标签。最近项目持久化、复制最近一条和整天复制仍待补充。

### 6. 优化工时输入和时间语义

当前主要以小时小数展示，例如 `1.5 小时`。对于日常记录，分钟表达通常更直观；快捷入口已覆盖常用的 15/30 分钟和整小时输入。

建议支持以下输入方式，并在内部统一保存：

- `30 分钟`
- `1 小时 30 分钟`
- `1.5 小时`

同时明确以下规则：

- 0 小时可以保存，但不能同步。
- 外部系统的计费精度和舍入方式。
- 跨午夜记录归属哪一天。
- 本地日期和远程工时日期使用的时区。
- 将来如果支持精确计时，区分日期、开始时间和结束时间。

### 7. 增强查询的快捷性和结果价值

当前查询支持日期、文本、标签和优先级，基础能力完整，但更像数据库筛选工具。

建议增加快捷条件：

- 今天、昨天、本周、本月。
- 未同步、同步失败。
- 有备注、无标签。
- 指定项目。

查询结果建议增加：

- 同步状态。
- 按项目汇总耗时。
- 按日期汇总耗时。
- 复制汇总结果。
- 导出 CSV 或 Markdown。
- 筛选“本地有记录但同步状态异常”的事项。

已完成基础版本：查询页提供今天、昨天、本周、本月快捷日期；结果摘要包含记录数和耗时合计；有结果时可以导出为 CSV 或 Markdown。按项目/日期分组汇总、同步状态快捷筛选和更丰富的导出字段仍待补充。

## P1：首次使用和导航

### 8. 增加首次启动引导

首次启动不应直接把用户带入数据库迁移、插件诊断或高级配置。

建议提供三步引导：

1. 选择或创建本地数据库。
2. 创建第一条工作记录。
3. 可选配置外部 Tracker。

未配置 Tracker 时应明确提示：

> 当前未连接任何外部系统，但仍然可以正常记录本地工时。

这样可以避免用户把“没有远程 Tracker”误解为“程序不可用”。

### 9. 收敛 Tracker 配置和高级管理

随着 Tracker 增多，动态页面和插件诊断入口可能使主导航越来越复杂。

建议：

- 主导航固定保留“今天”“查询”“设置”。
- Tracker 配置统一放入“外部系统”。
- 编辑器只显示当前记录需要的 Tracker 绑定信息。
- 多 Tracker 时显示实例名称和同步状态。
- 插件启用、禁用、卸载、诊断等操作放入高级设置。
- 将“保留数据卸载”“删除数据”等技术文案改成面向用户的数据和影响说明。

配置页已调整为按 Tracker 提供者分 Tab 展示；每个提供者内部继续负责自己的多实例管理，避免多个配置页面纵向堆叠。

## P2：脚本和高级功能

### 10. 脚本管理分为普通用户和开发者视图

当前脚本管理页面包含运行时诊断、目录诊断、执行历史和运行日志。这些内容对开发者有用，但普通用户更关心自动规则是否启用、最近是否成功以及产生了什么记录。

建议分为：

- 自动化规则：模板、启用状态、触发条件和最近执行结果。
- 开发者脚本：语言、入口、Worker 和脚本源码。
- 高级诊断：运行时、HostCall、进程和详细日志。

脚本失败时先显示“发生了什么、是否影响工作记录、如何处理”，再允许展开技术诊断。

### 11. 自动化脚本增加试运行和副作用预览

对会自动创建工作记录、应用模板或绑定 Tracker 的脚本，建议提供：

- 试运行。
- 执行前预览。
- 显示将新增哪些记录和多少小时。
- 显示可能同步到哪些 Tracker。
- 自动化执行历史。
- 单独禁用某条规则。
- 防止重复执行的提示。

## 建议实施顺序

### 第一阶段：同步安全和状态表达

1. 分离本地保存状态和远程同步状态。
2. 增加批量同步预览、确认、逐条结果和失败重试。
3. 按上传状态允许删除未上传或误写记录，并在已上传或状态不确定时给出明确提示。
4. 完善数据库、插件和远程同步失败的恢复操作。

验收标准：用户可以明确知道记录是否已保存、是否已同步；远程失败不会丢失本地记录；部分成功不会被误认为全部失败或全部成功。

### 第二阶段：日常记录效率

1. 增加最近项目和最近标签。
2. 增加复制昨天、复制整天和快速工时输入。
3. 增加分钟输入和统一的时间精度、时区说明。
4. 增加查询快捷条件、汇总和导出。

验收标准：用户能够用更少的输入完成一条日常工作记录，并能快速得到按项目和日期汇总的耗时结果。

### 第三阶段：恢复体验和高级功能

1. 首次启动引导和外部系统配置分层。
2. 脚本普通用户视图、试运行和副作用预览。
3. 移除或实现未完成的周/月同步入口。

验收标准：普通用户不需要理解 Worker、HostCall 或插件生命周期，也能完成记录和同步；Tracker 专项体验优化不阻塞本阶段交付。

## 与现有设计的关系

- 用户手工创建的工作记录允许删除；脚本自动化继续采用追加式模型，不提供删除或直接改写历史记录。
- 所有脚本语言继续通过 Worker 执行，本文件不建议引入进程内脚本作为用户体验优化方案。
- Tracker 继续通过插件边界扩展，体验优化应优先改进通用编辑器、同步状态和错误恢复，不把专用 Tracker 逻辑加入核心模型；Jira 专项体验优化暂不纳入短期计划。
- PLM 当前没有开放 API，继续保持待接口开放后的独立 Tracker 规划。
