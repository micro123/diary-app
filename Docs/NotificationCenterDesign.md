# 通知中心设计

## 1. 目标

Toast 和普通通知仍负责即时反馈，通知中心负责补足用户没有及时看到提示时的回看能力。通知历史不替代应用日志：历史只保存用户可理解的摘要和稳定操作入口，完整异常、堆栈与诊断数据继续写入日志。

状态栏只展示铃铛、未读数量和最高未读级别，不常驻显示全部历史内容。点击铃铛在当前窗口打开紧凑 Flyout，不新增导航页面或模态窗口。

## 2. 保留策略

进入统一宿主通知管道的 Toast 和通知均显式携带 `NotificationRetention`：

| 值 | 行为 | 典型用途 |
| --- | --- | --- |
| `Transient` | 只显示即时提示，不进入通知历史，也不增加未读数 | 已复制、导入事项不可编辑、参数校验、没有可操作数据 |
| `Session` | 进入本次运行的通知历史，退出程序后丢弃 | 普通保存、复制、导入导出和脚本运行完成 |
| `Persistent` | 进入通知历史并写入本地文件，重启后继续显示 | 数据库、Tracker、更新、备份还原和脚本异常，结果不确定或需要后续处理的操作 |

兼容现有调用的默认值为：

- `ToastEvent` 默认 `Transient`；
- `NotifyEvent` 默认 `Persistent`；
- UI 异步操作未处理异常强制使用 `Persistent`，并提供“打开日志”；
- 脚本主动请求的宿主通知默认 `Session`，避免第三方脚本无限写入持久历史。

页面内部直接使用局部 `NotificationManager` 的旧提示只承担当前页面的瞬时反馈，不进入历史。需要回看、跨页面处理或跨重启保留的调用必须改用统一事件管道并显式选择保留策略。

通知级别和保留策略互相独立。警告或错误不会自动强制持久化，但重要错误调用点必须显式使用 `Persistent` 或沿用 `NotifyEvent` 的持久默认值。

## 3. 数据模型

通知记录包含：

- 唯一 ID；
- 首次发生时间和最后发生时间；
- 信息、成功、警告或错误级别；
- 保留策略；
- 标题和正文摘要；
- 重复次数；
- 已读状态；
- 至多一个稳定操作，包括按钮文字、命令名和可选普通参数。

操作不保存委托。第一版只允许数据库设置、Tracker 设置、检查更新、打开当前日志和打开已存在本地路径；未知命令仍保留通知正文，但不显示操作按钮。

## 4. 历史规则

- 最多保留 100 条，最长保留 30 天；
- 超过数量上限时优先移除最早的已读记录，全部未读时移除最早记录；
- 保留策略、级别、标题、正文和操作完全相同的通知，在 10 分钟内重复时合并；
- 合并通知更新最后发生时间和重复次数，并重新标记为未读；
- 打开通知中心时，将打开前已经存在的通知标记为已读；面板打开后新到达的通知仍保持未读；
- 支持全部已读、单条删除、清空已读和确认后清空全部。

## 5. 持久化与安全

持久历史保存到应用数据目录的 `NotificationState/history.json`，不修改业务数据库结构。文件使用版本化 JSON 和同目录临时文件原子替换；应用退出清理阶段等待已排队写入完成。

写入前执行以下限制：

- 标题最多 256 个字符；
- 正文最多 4096 个字符；
- 对 API Key、Token、Password、Secret 和 Authorization 等常见键值执行脱敏；
- 不保存异常堆栈，完整异常继续进入滚动日志；
- 只有 `Persistent` 记录写入磁盘，`Session` 记录只保存在内存中。

损坏、无法读取或无法写入历史文件不会阻止程序启动和退出，只记录警告日志。

## 6. 界面

状态栏日期左侧固定显示通知铃铛：

- 无未读通知时不显示数字和状态点；
- 未读数量超过 99 时显示 `99+`；
- 状态点使用最高未读级别，错误优先于警告、成功和信息；
- Flyout 内容宽度约 400px、最大高度约 500px，历史列表独立滚动；
- 面板和通知项使用接近不透明的主题实体表面，避免桌面或主内容透出后降低可读性；Flyout Presenter 本身保持透明、无边框、无内边距，只由通知中心面板绘制单层外轮廓，避免主题容器与内容容器形成双重边框；
- 每条通知使用轻边框卡片，显示左侧级别色条、标题、时间、可选正文、重复次数、操作按钮和弱化的删除入口；
- 未读项使用轻微语义色背景和标题字重，已读项回到普通卡片层级，不使用大面积高饱和状态色；
- 顶部“全部已读”和底部清理操作使用低权重文本按钮，清空全部以错误语义色区分；没有历史时隐藏底部操作区；
- 空历史直接显示“暂无通知”。

## 7. 服务边界

`NotificationHistoryService` 订阅 `ToastEvent` 和 `NotifyEvent`，负责保留策略、历史、已读、去重、清理、脱敏和持久化。它在应用初始化阶段创建，因此不依赖主窗口是否已经显示。

`AppStatusService` 继续只表达当前数据库、Tracker、后台任务、更新和短时全局消息，不保存历史。`StatusBarViewModel` 同时读取当前状态快照和通知历史快照，但不依赖具体业务页面 ViewModel。

## 8. 验证

- 单元测试覆盖默认保留策略、Transient/Session/Persistent 边界、跨重启加载、重复合并、重新未读、脱敏、截断和容量淘汰；
- 状态栏 ViewModel 测试覆盖未读数量和通知列表映射；
- `ui-core-full` 检查通知中心入口，并真实打开 Flyout；
- Linux X11 原生窗口检查 Flyout 位于底部状态栏上方，不向窗口底部溢出；
- 深浅主题和 1280×800 窗口下检查铃铛、未读徽标、卡片、滚动区和操作区。
